# TaskFlow 面试问答

### 1. 为什么选 Redis Streams？

现有系统用同一 Redis 实例保存任务 Hash 和消息 Stream。Streams 提供有序条目、消费者组、确认以及 PEL 恢复，Lua 可以把同实例的任务状态和消息变更作为一个隔离操作执行。单 Redis 也约束了容量与故障域。

### 2. Redis Streams、RabbitMQ 和 Kafka 有什么区别？

Streams 使用 Redis 键管理条目和消费组，适合本项目的紧凑部署。RabbitMQ 以交换机和队列路由为核心，具备多种确认与路由机制。Kafka 使用分区日志和消费位点，适合较大规模的保留及回放。三者的吞吐、持久化、运维和重投递细节应结合部署评估。

### 3. Consumer Group 如何分配任务？

Worker 对同一个组使用 `XREADGROUP … >`。新条目分配给组内消费者，加入 PEL。每个进程使用带随机后缀的消费者名。多个进程共享组进度并各自处理分到的消息。

### 4. `XACK` 改变了什么？

它把消息从该组的 PEL 移除，Stream 条目本身仍保留。TaskFlow 在成功、最终失败或发布重试后确认当前消息，读到已终态的重复消息时也会确认。

### 5. 哪些情况会重复执行？

Worker 在转换完成后、提交成功前退出，后续 Worker 会再处理。租约过期后新 Worker 也可接管，旧转换可能仍在运行。重复消息由状态和租约守卫限制对业务结果的影响。

### 6. 至少一次投递与恰好一次执行有什么关系？

交付成功的响应和实际执行可能处于不同的故障边界。Redis 有 PEL 时可以再次投递，执行器可能因此运行多次。业务保护提供单一的可见成功引用，前提是状态与结果存储仍可用。

### 7. 项目的幂等范围是什么？

以任务 ID 为边界。终态的重复消息不重新转换，执行中只有持有效租约的令牌能提交。同一 PDF 被主动上传两次会生成两个任务。

### 8. 两个 Worker 同时领取时会怎样？

同一 Redis 上的 Lua 串行执行。第一个领取者写入执行令牌和到期时间。第二个看到有效租约时返回 `busy`。租约到期后，新的令牌可以获得提交权。

### 9. Worker 中途崩溃怎么办？

未确认消息保留在 PEL。其他 Worker 用 `XAUTOCLAIM` 扫描并重新领取，处理权仍受任务租约和预算约束。故障脚本实际强制结束原进程并验证了下载结果。

### 10. 为什么要同时使用超时、租约和最小空闲时间？

超时限制本进程读任务和运行 Poppler 的时长。租约决定 Redis 何时允许接管与提交。最小空闲时间控制 PEL 扫描何时能回收消息。它们约束的对象不同。

### 11. fencing token 在这个项目里是什么？

每次领取都用新随机令牌替换 `owner`。Redis 在成功和失败提交时比较令牌并检查到期时间。用于这里的是比对型代次标识。外部系统若要拒绝乱序写入，通常还需要可比较的单调版本。

### 12. 提前 `XAUTOCLAIM` 为什么不能直接 ACK？

提前迁移的是消息归属，旧 Worker 可能依旧有合法的任务租约。直接 ACK 可能移除唯一的恢复入口，尤其当旧 Worker 随后崩溃。新版遇到 `busy` 保留消息。

### 13. Redis 持久化能保证绝对不丢吗？

Compose 使用 AOF `everysec`。故障可能丢失最近写入，恢复旧快照也可能丢失更新。Redis AOF 和文件卷分别需要备份，恢复后要校验引用。

### 14. 为什么第一版没有 MySQL？

任务元数据与消息都由 Redis 管理，单实例方案便于验证 Lua 状态转换。关系数据库可用于报表、审计和独立持久化，接入时需要设计数据库与消息之间的发布协议。

### 15. Worker 怎么横向扩容？

Compose 调整 Worker 副本数。进程使用独立消费者名，读取同一 Redis 的同一消费者组，并挂载同一数据卷。每个进程执行一个转换，副本数控制并行度。

### 16. goroutine 和 OS 线程是什么关系？

Go 调度器将 goroutine 映射到线程执行。HTTP 并发来自独立请求的 goroutine。Poppler 是另一个 OS 进程，CPU 与内存需要单独统计。

### 17. channel 和 mutex 如何选择？

通道适合传递事件或归属，API 用缓冲通道接收服务器退出结果。互斥适合共享进程内状态的临界区。跨 Worker 进程的任务状态用 Redis Lua 约束，因为各进程的 Go 锁独立。

### 18. Context 如何取消任务？

进程信号会取消 Worker 循环。Redis 客户端为活跃连接注册取消回调。转换中用 `exec.CommandContext` 终止 Go 启动的 Poppler，随后由 PEL 恢复。终态提交使用独立的短时 Context；已经运行的 Redis Lua 不会因为客户端离开而回滚。

### 19. 如何定位性能瓶颈？

分别测 API-only、完整链路与 Poppler-only，并检查 Go pprof 和子进程资源。固定样本中 Poppler 子进程使用大部分 Worker 路径 CPU。Go CPU 栈还观察到 Redis 连接相关开销。

### 20. 如何分析 P95？

区分排队和转换，先用 `started_ms - created_ms` 观察排队，再检查 Worker 执行耗时和尝试次数。完整链路统计是 Redis 创建到终态的时间。上传前网络延迟应通过客户端另测。

### 21. 增加 Worker 后吞吐为什么会停滞？

Worker 共享机器 CPU、内存、文件系统和 Redis。转换与轮询会产生资源竞争，增加进程可能使调度和 I/O 成本上升。本次测试只测到八个 Worker。

### 22. 可靠性有哪些边界？

Redis 及共享卷分别持久化。进程故障经过恢复测试，跨系统原子性和主机级故障依赖外部设计。项目没有 Redis HA、对象存储、长期保留策略或跨主机文件复制。

### 23. 跨机运行最先改哪里？

用所有进程可访问的持久对象存储代替本机共享卷。保留每次尝试不可变对象键，通过 Redis 或数据库 CAS 发布获胜引用。还需处理认证、凭据、GC 和故障域。

### 24. Redis 完全丢失后还能恢复吗？

可从匹配的 Redis 备份和文件快照恢复。如果只剩输入文件，必须用外部记录重建任务或重新提交。文件名能帮助识别，无法直接恢复任务的尝试历史和完成状态。

### 25. 怎样演进为更通用的任务调度平台？

在已有执行器接口上增加任务类型和参数，建立统一错误分类，添加限流、延迟重试、优先级与资源配额。再按可靠性目标决定持久化、调度和存储分层。

### 26. 为什么这个项目超出了简单 CRUD？

HTTP 请求与任务执行跨进程和故障域。需要考虑消息归属、执行所有权、重投递、进程退出以及文件与元数据的提交边界，并用故障测试证明这些行为。

### 27. 结果提交的回执丢了怎么办？

Worker 不能判断 Lua 是否执行成功，暂时保留该尝试的结果候选。终态引用始终以 Redis 为准。离线核对会保留仍被 Redis 引用的结果，处理已确认的孤儿文件。

### 28. 为什么 Lua 脚本还需要小心命令顺序？

Lua 运行时的隔离可以防止其他客户端看到中间状态，运行错误不会回滚已经执行的写入。重试脚本用 `XPENDING` 检查组后再入队，随后更新状态和确认。独占键空间与容量保障是正常运行条件。
