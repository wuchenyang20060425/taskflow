# 可靠性与恢复协议

## 状态转换

| 当前状态 | 条件 | 结果 |
| --- | --- | --- |
| 无 | 文件保存后提交创建脚本 | `queued`，并写入首条消息 |
| `queued` 或租约已过期的 `running` | 尝试预算可用 | `running`，尝试次数加一并签发新执行令牌 |
| `running` | 有效租约持有者提交成功 | `succeeded`，记录结果引用并确认消息 |
| `running` | 有效租约持有者提交失败，预算尚有余量 | `queued`，写入重试消息并确认原消息 |
| `running` | 有效持有者提交失败且预算用完，或恢复时已无预算 | `failed`，确认当前消息 |
| 终态 | 再次收到相同任务消息 | 确认消息，保留原终态 |

Redis `TIME` 决定租约与延迟时间戳。值为随机令牌的 `owner` 充当 Redis 提交的执行代次标识，Lua 对它做相等校验，并检查 `lease_until`。令牌不单调递增，外部资源需要独立的版本协议。这里通过不同文件名隔离两次执行。

`XAUTOCLAIM` 改变消费者组中的消息归属，并返回下一次扫描游标。消息归属和任务租约独立。如果取到的消息仍有有效租约，Worker 保留它在 PEL 中，因为它可能正是原进程处理的那条消息。这样原进程随后崩溃，消息仍能在达到空闲阈值、租约到期后恢复。默认恢复延迟还受扫描工作量和最多约一秒的新消息阻塞窗口影响。

## 文件及状态提交

1. 上传文件由 API 以排他创建方式写入服务端命名的路径。读取失败、超限或确定尚未入队的请求取消会移除本次写入。
2. Poppler 写入当前尝试专属的 `.partial` 文件。检查转换和可提取文本后，在同目录内重命名为候选结果。
3. Redis 脚本检查状态、执行令牌和到期时间，并在同一次执行中确认消息和设置成功引用。用户通过该引用下载。
4. 明确收到过期拒绝时，Worker 删除自己的候选。遇到 Redis 连接错误时保留候选，因为脚本有可能已提交并且只有回执丢失。上传时同理。

注册文件、文件重命名与 Redis 脚本跨越两个存储系统。进程中断时可能保留未引用文件。主机断电、磁盘损坏或 Redis 恢复到不相容的快照时，已经提交的引用也可能失效。API 在结果丢失时返回可观测的 `500`。部署应配套备份两类状态。

Lua 提供单实例内的隔离执行，运行时错误没有自动回滚。部署需保护 Redis 键类型和消费者组，并保持磁盘与内存容量。失败重试先确认消费者组可用，再写入新消息。严禁在存在未确认任务时随意裁剪 Stream 或删除消费者组。Redis 的 AOF `everysec` 存在故障时的数据丢失窗口，Redis 完全丢失时需要依靠备份恢复或重新提交。

## 孤儿核对

备份 Redis 和文件卷，校验二者属于同一环境，并停止全部 API 和 Worker，保持 Redis 运行。先运行默认的候选清单，确认后才显式应用。工具只扫描匹配任务命名规则且达到最小年龄的普通文件，保留任务关联的上传及 Redis 当前引用的结果。

```bash
go run ./cmd/reconcile -data ./data -min-age 24h
go run ./cmd/reconcile -data ./data -min-age 24h -apply
```

Compose 环境可在停服后使用 `docker compose run --rm --no-deps api taskflow-reconcile` 查看清单，并按需加上 `-apply`。Redis 数据发生丢失或卷来源不明时，应从备份重建关联再执行核对。

## 当前边界

- Redis 持久且消息未被移除时提供至少一次投递。相同 PDF 的重新上传会创建新任务，客户端上传重试存在产生新任务的可能。
- 转换错误采用有界立即重试，终态保留错误。没有延迟重试、死信队列或自动的消息归档。
- 运行依赖单 Redis 和同一主机共享卷。跨主机部署需持久化任务元数据和结果对象，再以共享存储支持不可变结果键和原子引用。
- 目前未提供身份鉴权、配额或 PDF 沙箱。Compose 只在本机回环端口发布 API。面向外部服务前需要访问控制、资源限制及定期升级转换程序。
- 状态和消息历史持续增长，单 Redis 的内存、AOF 和文件卷需要容量监控。`/ready` 反映 API 的 Redis 连通性与本机目录可见性。
